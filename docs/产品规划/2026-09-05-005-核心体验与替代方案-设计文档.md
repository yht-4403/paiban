# Accord 核心体验与替代方案

> 2026-09-05。按 JC 指定的 About Face 4 目标导向方法评审现有产品。依据：本轮实际完成的 GPT / Codex + 飞书 + harness 文档同步、团队 PRD、MVP 实测和官方竞品资料。人物画像与未来场景均为待验证假设；本文提出产品收敛建议，不表示新功能已实现。

## 1. 当前判断与设计范围

**在整理资料、更新文档、共享知识和据此问答这部分，你刚搭好的工作流与 Accord 确实提供同一类价值。独立软件不会自动产生本质差距。**

现有组合已经有本地版本记录、固定云端链接、发布规则、身份授权、工具调用和同步校验，不能把它贬低为“复制粘贴”。如果再加上持久状态、可靠触发和业务权限检查，它也能实现更完整的协作产品；产品可以依托飞书或成为插件，未必需要另建工作台。

Accord 值得验证的增量是：**让一次跨人请求从有据可查，走到该确认的人作出明确决定，并将结果可靠地交给下一位执行者。** 是否能减少追问、等待和维护成本，需要与现有组合实测比较。目前没有不可替代性、付费意愿或长期留存的证据。

本次输出核心行为、对象与状态、竞品定位、验证方法和路演提纲。近期以在建 Web 主流程验证；长期载体可以是飞书内的轻量入口。前端按已选定的 Tutti 接入计划推进，本文的产品建议不撤销该实施决定。比赛仍于 2026-09-06 12:00（UTC+8）截止，本次不据此扩大为办公平台重建。

## 2. 主用户与关键假设

以下画像来自现有材料与当前协作的启发，不是经过访谈聚类得出的研究结论。

| 角色 | 假设型画像与行为 | 目标、能力与设计取舍 |
| --- | --- | --- |
| 主要人物画像 | 2～15 人项目小队中推进交付的人；会用 AI 和飞书，经常依赖别人提供信息或作决定，但不愿维护 CLI、鉴权和同步脚本 | 在截止前拿到可信答复、明确责任和下一步；知道“我还在等谁”。优先消除追问与重复交代 |
| 次要人物画像 | 被依赖的专业成员；同时有自己的交付工作，能回答关键判断，反复被问同一批进度问题 | 保留专注时间，避免 Agent 替自己承诺；只处理真正需要自己的问题 |
| 购买者画像 | 小队负责人或工作室主理人，可能与主用户重合 | 是否值得花钱取决于净节省的协调成本；不能用管理者的监控诉求牺牲成员信任 |
| 利益相关者 / 被影响者 | 项目成员、资料所有者、任务接收者；企业接入时还有管理员 | 能看到自己的信息何时被共享、承诺如何形成，能纠正和撤回授权 |
| 排除画像 | 单人工作、只需通用问答的人；享受自己维护完整自动化体系的专家；期望全天监控成员的管理者 | 不为他们增加复杂配置或监控面板。JC 的熟练程度也可能让我们高估普通成员愿意承担的配置成本 |

主要画像的心理模型是“请某位同事帮我把一件事推进”，而不是“编排一组 Agent”。日常设计面向已熟悉基本流程的中级用户，入门说明完成使命后应收起。

待验证的关键假设：资料可查后，仍有足够多的请求卡在人的判断与承诺；成员愿意让助手代答已授权的事实；减少打扰没有以增加等待和误答为代价；团队愿意采用一个额外入口。用户频率、痛点强度、付费意愿均未测量。

## 3. 当前状态：我们刚刚实际怎么做

已观察到的路径：JC 指定资料与目标 → Agent 阅读本地和飞书材料 → 整理 docs → JC 要求发到健城文件夹 → Agent 建目录、写正文、维护文档映射并回读 → 队友在拥有相应权限和工具接入时可以继续查阅。

这个路径已经实现了知识沉淀和分发。它的维护工作由 JC 发起需求、Agent 理解并执行，持久规则保存在 AGENTS / harness，具体发布在活跃任务中完成；当前没有文件监听器或无人值守同步服务。**尚未实际验证队友用自己的 GPT 身份接入，也没有因为创建在个人分类文件夹内就额外扩大权限。**

仍需进一步观察的摩擦是：队友是否知道问哪里、是否能区分旧计划与新承诺、请求未解决时由谁跟进、多个助手同时更新时是否一致。不能把这些假设写成已测量痛点。

现有 MVP 的实测还表明，私人快照泄露、无身份写状态、无关聊天完成任务、旧会议接口绕行和时区错误会破坏信任。因此，现阶段不能宣称 Accord 比飞书或 GPT 的权限更可靠。详见 [原型验收](2026-09-05-003-现有原型评估与比赛收口-验收记录.md)。

## 4. 从功能回到用户目标

| 现有功能说法 | 用户真正要的结果 | 应消除或弱化的系统任务 |
| --- | --- | --- |
| 每人一个 Agent | 常见问题有人接住，关键判断由本人负责 | 不强迫每人配置角色提示词、模型和工具链；技术上不要求每个人都有常驻独立进程 |
| 随时同步 docs | 队友拿到可验证、足够新的信息 | 不让成员手工搬文件、修链接、挑同步格式 |
| 找同事 | 拿到可信答案或明确的答复预期 | 有共享答案时直接给答案；不必先逛成员列表、再挑哪个 Agent |
| 任务分配 | 下一步有人明确承接 | 不把“建议负责人”“被指定”“本人承诺”混成同一种状态 |
| AI 会议 | 对分歧作决定并推动工作 | 能异步解决就不召集会议；会前整理和会后待办不是额外产品目标 |

终点目标：依赖得到解决，负责人和时间明确。体验目标：确定、受尊重、有掌控感。业务目标：让团队愿意反复使用，最终验证付费。技术目标：身份、可见范围、状态和恢复可靠。

主要冲突是 A 想尽快得到答复，B 想少被打断。不能只优化“打断次数”：如果系统把所有请求藏起来，打断下降但交付更慢。应同时展示答复预期、超期状态和紧急升级选项。

## 5. 核心场景与体验路径

### 背景场景

以下是用于设计的示例，不代表队友已作出承诺：明天要演示，A 需要确认登录接口能否在上午 10 点交给前端；B 正在开发。共享文档只有昨天的“预计明早可用”。A 真正需要的是能据此安排工作的答复。

### 主路径

| 步骤 | A / B 做什么 | 系统行为与完成反馈 |
| --- | --- | --- |
| 1. 提出问题 | A 问“登录接口现在什么状态？” | 查 A 有权看到的共享资料，展示来源、更新时间、事实 / 计划性质；可以直接回答，不要求先选 Agent |
| 2. 识别仍需判断的部分 | A 接着问“能确认明早 10 点交付吗？” | 历史计划不能当新承诺。提示“现有材料没有这项确认，需要 B 决定”，保留上下文 |
| 3. 明确请求本人 | A 点“请 B 确认”，看到问题、依据、答复期限和接收人 | 创建一个持续可见的事项，显示“等待 B 确认，预计何时提醒”；不要求重新复制整段聊天 |
| 4. 最小必要打扰 | B 在合适时机看到卡片 | 卡片只显示要决定什么、当前依据和影响；可以确认、修改时间、拒绝或要求补充。打开 / 已读不等于承诺 |
| 5. 本人作出决定 | B 点击“确认明早 10 点交付”，或提交替代时间 | 明确记录 B、确认的具体内容和版本；这次动作本身就是确认，不额外连续弹三个确认框 |
| 6. 落实并交接 | A 看到结果，继续安排前端工作 | 按预览过的作用范围更新任务 / 共享结论，显示写入回执；失败则保留已确认决定并提示“任务待同步”，不伪装全成功 |

文字流程：**提出问题 → 查授权依据 → 能回答就答复；需要人的新决定 → 明确找本人 → 本人确认或改约 → 结果落实、状态可追溯。**

这不要求所有问题都绕经一位“同事 Agent”；有现成共享答案的请求应尽早结束。也不应让每次日常对话都触发写记忆或改任务。会议是在多人分歧无法异步解决时的扩展入口。

### 验证场景与恢复

| 场景 | 应有反馈和恢复 |
| --- | --- |
| 文档陈旧或互相矛盾 | 显示不同来源与日期，不自动把较新的文本等同于事实；请责任人澄清 |
| A 无权读 B 的草稿 | 服务端不向 A 或 A 的模型发送原文；提供申请授权或请求本人答复路径 |
| B 在勿扰 / 离线状态 | A 看见排队时间、答复期限及超期状态；到点不静默消失，不默认惊扰所有人 |
| 模型失败或判断不确定 | 保留问题与证据，允许直接请求本人；清楚显示未完成代答 |
| B 打开旧版本确认卡 | 提醒事项已改，展示差异，不能用旧确认覆盖新约定 |
| 双击确认、断线重发 | 同一动作只产生一次有效承诺和写入；刷新后状态保持一致 |
| 飞书写入失败 | 显示“B 已确认，任务写入失败”，仅重试未成功的步骤 |
| 承诺后改期 / 撤回 | 保留原记录、写入新状态并告知受影响者；不能通过删除历史假装从未承诺 |

撤回读取权限只能限制后续访问，不能保证收回别人已看过或另存的内容；产品说明不能作这种不现实的承诺。

## 6. 需求推导与交互框架

数据元素：问题、发起人与责任人、资料出处与版本、可见范围、答复截止、已确认内容、执行结果。功能元素：检索、补充、请求确认、改约、拒绝、撤回、重试、查看历史。将它们组织成以下对象，而不是直接照搬数据库表：

| 核心对象 | 用户能看到与操作的内容 | 服务端必须保证的边界 |
| --- | --- | --- |
| 协作事项 | 我问了什么、在等谁、何时答复；补充、取消、调整期限 | 各参与者看到同一事项版本；变更不能伪造他人身份 |
| 依据 | 来自哪里、何时更新、事实还是计划；打开原文、纠错 | 依调用者权限选择内容；对方 Agent 的访问权限不自动转给请求者 |
| 已确认决定 | 谁确认了什么、影响哪些工作；改约、查看历史 | 明确操作者、内容版本和有效状态；模型建议不能代替人的新承诺 |
| 后续行动 | 谁负责、截止、进度、交付证据；接受、更新、完成 | 分配与接受区分；没有预先派工授权时，不把第三人被指派当作其已承诺 |

协作事项的表现状态：`查找依据 → 已答复`，或 `待补信息 → 待本人确认 → 已确认 → 落实中 → 已落实`；旁路有 `已取消 / 需重试 / 已变更`。任务进度另行表达，不能把“问题已回答”“本人已承诺”和“工作已完成”混成一个勾选框。

**姿态建议：后台守护为主、短暂处理为辅；长期可依附飞书或成员已有的 AI 工具。** 这与桌面 / Web 平台选择无关。减少打扰的产品，不应要求所有人常驻另一个重型桌面。当前 Web MVP 只是便于验证行为的载体。

建议主导航按目标组织：

- **待我处理**：需要本人判断的事项，直接给出可操作的决定卡。
- **我在等什么**：发起的请求、责任人、答复时间和阻塞原因。
- **共享结论**：可查证的事实与已确认决定，关联其来源和行动。

发起问题入口保持稳定；成员选择和资料列表按需展开。个人工作台可以保留，但不应成为使用核心协作的强制前置步骤。上述是后续界面设计简报，不是要求在本轮立即重排全部页面。

## 7. 细节审查：防止产品自己制造工作

- 首次只完成身份与合理默认范围；高级模型配置、汇报窗口、分类规则延后。已有项目信息自动带出。
- 查阅、草稿整理、已授权的常规同步不反复弹确认；明确共享边界、新承诺和影响他人的动作提供可见预览与控制。
- “问 Agent / 找本人”不能成为隐藏模式。发送前显示接收方，切换时说明哪些内容会交给本人。
- 同一事项内补充、确认、查结果，减少聊天、任务、会议页面之间的往返。
- 非紧急事项用稳定状态和集中提醒，真正需要判断才主动通知；不能把“静默”当成“丢失”。
- 手机上的确认卡不依赖 hover，按钮可触达、长内容可展开，中断后保留草稿；桌面端保留快捷操作和稳定布局。
- 改期、取消、草稿编辑支持恢复；已发送的承诺用更正记录处理。错误文案解释用户下一步能做什么。

## 8. 与 GPT + 飞书 + harness 的差距可以是多少

| 能力 | 当前组合 | Accord 的合理要求 |
| --- | --- | --- |
| 整理、总结、共享、检索文档 | 已覆盖大部分，本轮同步已有实际证据 | 作为基础能力，不能作为主要差异 |
| 规则与持续上下文 | AGENTS / harness / 文档映射已经承担一部分 | 不要求成员重复描述项目或背诵规则；采用已有工具也可以 |
| 读取与写入授权 | 飞书已有权限，工具有自己的授权约束 | 每一次跨人查询和写入正确沿用这些边界；不能借“代答”扩大权限 |
| 跨人的请求、承诺和回执 | 可以用任务、表格、工作流和执行脚本搭建；本轮只验证了文档发布 | 提供开箱可用且可理解的流程，减少每个团队重新搭建与维护 |
| 触发、并发与故障恢复 | 可编程实现；当前约定没有部署后台服务 | 关闭聊天窗口后仍保留承诺；重试不重复，部分失败看得见 |
| 团队使用成本 | 对 JC 这类熟练使用 Agent 的人可能已经足够好 | 对目标小队明显降低配置、学习、追问和维护成本，否则增量不成立 |

**没有一条是通用模型加工具从技术上不能实现的。** 如果 harness 已包含完整执行程序、持久状态和权限检查，它本身就在构成软件。写在规范里的要求、一次正确执行和多身份 / 多次故障下持续满足要求，是不同的验证层次；并非“Markdown 天生不行、专用软件天生可靠”。

因此可以有三种诚实的产品结果：一套好用的协作模板 / Skill 包、飞书上的协作插件、或有独立服务的产品。选择应取决于使用成本与可靠性，不能由“必须做一个新 App”倒推需求。

## 9. 外部竞争：我们还没有证明领先

| 替代品 | 已知重叠与强项 | Accord 需要证明什么 |
| --- | --- | --- |
| ChatGPT 共享项目 / 公司知识 / Apps | 共享项目提供项目上下文；公司知识可利用授权数据源；部分 Apps 能执行写操作。不能宣称 GPT 只能聊天、没有权限或不会用工具 | 特定团队协作流程能否更省步骤、更少维护、更好理解；不是有没有 AI 或文档 |
| 飞书 aily / 工作流 | 官方已提供知识接入、工具能力和可配置工作流，覆盖协作自动化所需的相当一部分底座 | 非技术小队是否能更快用起来；预置的人际请求流程是否有实际效果 |
| Tutti / Tutti VM | 本地工作台组织 Agent 与执行工具；VM 官方强调多人共享工作现场、上下文和 Agent 协作 | 在“找谁判断、何时打扰、谁作出承诺”这个窄场景能否做得更清楚，而不是与其比整套工具数量 |

以上是官方资料与已读源码的范围，不是对每个产品的全功能验收，也不意味着这些竞品没有确认、提醒或细粒度权限。我们的已测 MVP 尚有会破坏核心承诺的问题，差异目前是**产品假设**，不能写成“独有技术壁垒”。

## 10. 验证、风险与下一步

把已经搭好的 GPT + 飞书 + harness 当作对照组，而不是绕开它。用同类、难度接近的合成请求分别跑两套路径，交换顺序，避免第二次因为记住答案显得更快。至少覆盖查事实、请求新承诺、资料过期、改约和写入失败；记录原始事件，不用主观“感觉更智能”替代。

| 检查 | 记录什么 | 如何作决定 |
| --- | --- | --- |
| 推进效率 | 提问到可信答复 / 有效承诺的时长；人为催问与重复交代次数 | 比较同类事件，并区分真实等待与演示中的快进 |
| 打扰成本 | B 实际需要处理几次、花多久；无关通知次数 | 不允许靠延迟所有答复换取表面上的少打扰 |
| 信任与准确性 | 误答、越权、伪造承诺、过期确认、重复写入 | 这些作为必须通过的行为检查，不能用效率抵消 |
| 采用成本 | 接入、维护、处理冲突所花时间；队友能否独立完成一次请求 | 把配置时间也算进去，不只比较点按钮的几秒 |
