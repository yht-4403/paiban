# 项目进度与后续排期

Accord 已有可真实使用的 Web 协作基础：资料问答、同窗找本人、本人承接待办、文字群聊和异步课题。下一阶段应补消息通知与聊天收尾，再完善资料、会议和任务分配，最后推进开放记忆与桌面接入。

> 核对日期：2026-09-06，北京时间约 00:45。读者：JC 与产品、开发队友。依据为本机当前源码、最近验收记录和服务状态；不能用旧文档的阶段数字代表当前完成度。本次为进度审计和建议排期，没有实施下列待办、重新调用模型或向队友分配任务。

## 当前可以实际使用什么？

以下“可用”只代表对应范围已经接通，不等于该模块的全部目标功能已完成。

| 能力 | 当前可用范围 | 主要边界 |
| --- | --- | --- |
| 账号 | 创建空间、邀请、注册、登录、退出 | 单工作空间，缺账号恢复与完整成员管理 |
| 个人空间 | 文件夹、聊天移动、资料绑定；个人普通聊天删除、撤销和回收站恢复 | 删除不覆盖协作聊天；只可移除空文件夹 |
| 真实 AI | DeepSeek V4 Pro；获准资料检索、读取、引用、状态工具、停止与重试、思考强度设置 | 当前工具以读取为主，没有通用文件执行、沙箱或外部 Agent 宿主 |
| 找同事 | 同一个对话中问 Agent、转交本人、本人回复、确认任务；立即或定时送达 | 当前事项须先有一次完整 Agent 回答；定时送达不等于截止前处理 |
| 群聊 | 3–8 人建群、邀请、改群名、持久化消息、显式 @ 某位成员的 Agent | 新成员仅看加入后的消息；缺退群、移除成员、解散和群文件 |
| 待办 | 责任人确认、优先级、完成和重新打开 | 缺通用任务推荐、主动分配、截止日期和阻塞状态 |
| 异步课题 | 创建共同议题、各自探索、提交与撤回、统一公开、AI 比较、人做决定、交接 | 已实现的是异步方案工作流；不等于同步会、决策会的自动主持已实现 |
| 资料 | 正文及 Markdown/TXT 导入、资料集合、版本、私有/团队/课题范围；自动检索或指定资料 | 导入限 64 KB、正文 16000 字；不是任意文件上传或本地磁盘自动同步 |
| 工作状态 | 本人设置专注偏好；开启共享后显示 Accord 内工作/聊天及可见待办进度 | 不识别系统其他应用、思考状态或真实会议；无可靠事件就不能推断空闲 |

最近一轮验证为 52 项后端测试、类型检查、构建和 UI 规范检查通过。群聊曾完成隔离账号的真实模型与引用验证；Agent 先答规则最近使用模型替身和隔离接口响应验证。390 / 768 / 1440 三种宽度已有阶段验收，未做全面可用性研究或 Tutti 同尺寸逐像素对比。

本机 API 与 Web 服务本次检查正在运行。临时局域网入口由服务状态返回，关闭时间显示为 2026-09-07 00:00；README 中的旧 IP 和关闭日期已过时。正式公网部署、两台真实设备的完整当前版本验收，以及提交版本与本机改动的一致性仍须检查。

## 还缺哪些功能？

P0 是比赛交付前必须核对的事项；P1 是团队日常使用最先补的缺口；P2 是完整协作流程；P3 是平台化扩展。飞书单文档的本机只读试点已经完成，表中 P3 保留的是成员独立授权、目录同步与开放接口。

| 优先级 | 工作包 | 具体缺口 | 做完后应看到的结果 |
| --- | --- | --- | --- |
| P0 | 版本与交付 | 本机有大量未提交改动；README、阶段文档、访问入口与实际能力口径不一致；需双机回归 | 队友能运行同一份交付代码；路演只展示本次验收通过的真实能力 |
| P1 | 消息与通知 | 持久化已读/未读、AI 回答完成提醒、离开会话后回看、失败送达与重试；群聊目前由 Agent 生成阻挡普通消息 | 发完可离开，不漏回复；群内人在 Agent 生成期间仍可聊天 |
| P1 | 请求处理 | 接受、拒绝、补充信息、延期、撤回；加急与截止前处理；专注期和集中处理规则 | 知道请求送给谁、处理到哪一步；通知、回复与任务承诺分开 |
| P1 | 聊天收尾 | 任一方手动结束、30 分钟无消息结束、摘要、待办建议、负责人选择加入、记忆保存 | 没有任务也能正常结束；不会重复创建待办或扩大摘要可见范围 |
| P1 | 团队运行 | 固定 HTTPS 入口、持久存储、备份恢复、更新回滚、账号恢复、成员停用和邀请撤销 | 不依赖 JC 的电脑持续开机；能恢复数据并撤销离职/误邀成员访问 |
| P1–P2 | 群聊管理 | 退群、移出成员、群主交接、解散、归档；权限变化后的历史与资料规则 | 人员变化后可见范围保持正确，群聊能够完整管理 |
| P2 | 文件与共享 | PDF/DOCX 等文件解析与预览、进度和失败反馈、文件删除/恢复、版本对比；文件夹共享与权限继承、指定成员授权 | 用户可导入真实工作资料；拖动和换目录不会意外公开私人历史 |
| P2 | 工作记忆 | 自动记录获准范围内的进度、来源和更新时间；过程稿/已确认结论、版本确认、纠正和撤回 | 同事能了解未完成的工作，Agent 不把草稿或生成完成当作本人决定 |
| P2 | 任务推荐与分配 | 基于资料推荐 1–3 人、给出依据、发起者选择后进入负责人待办；截止日期、阻塞、交付物、筛选与归档 | 区分本人承接和他人分配，分配权限明确，任务可以追到交付 |
| P2 | 同步会与决策会 | 发起议题、向个人 Agent 收集上下文、汇总信息缺口、推荐必要参会人、邀请、文字会议、会后摘要与待办 | 同步会能用简报完成信息同步；决策会只邀请确有必要的人参与 |
| P2–P3 | Agent 与运行能力 | Agent 导入和配置、工具连接、历史迁移、产物写入、外部工具执行、隔离环境、多 Agent 调度 | 注册对应的云模型助手逐步升级为能接入用户现有工具的 Agent |
| P2 | 长会话管理 | 正文全文搜索、长记录分页、个人会话重命名、引用回复与定位、跨设备草稿 | 聊天数量与内容增长后仍能找到、继续和理解上下文 |
| P3 | 开放记忆与商业化 | 成员独立 OAuth、飞书目录增量同步、只读 MCP/HTTP 接口、本地监听与补传、桌面安装更新；企业 SSO/多租户/审计、预算与计费、开源发布 | 不再依赖工作空间创建者的本机登录；第三方 AI 能按权限读取记忆，部署和服务收费有真实运行依据 |

当前已经有资料工具轨迹、引用和用量记录，不应再把它们写成完全缺失。尚缺的是通用执行工具、可交付产物，以及面向长期使用的运行与费用管理。当前每人同一时刻只运行一条回答，工作进程最多并行两条，扩容前需调整队列与存储方式。

模型可靠性贯穿 P1：分别量测排队、检索、首字和总响应时间，先优化检索与重复读取，再依据答案质量评估思考策略。当前完整回答门槛保持执行；网络、额度或模型故障需要明确重试与恢复，不偷偷解锁绕过 Agent 的路径。

## 前端 UIUX 最先需要梳理什么？

先补完整状态和操作结果，再做视觉微调。以下“产物”指需要补齐的状态图或界面规格，不代表要增加独立页面或弹窗。

| 顺序 | 真实问题 | 需要梳理的交互产物 |
| --- | --- | --- |
| 1 | Agent 回答完但用户已离开，列表不能可靠表达未读；请求数也不等于消息未读数 | 统一消息状态：生成中、回答完成未读、待本人回复、已回复；收件箱角标与每人已读位置 |
| 2 | 个人空间中的“需要你”页面仍叫“待我拍板”；“我的待办”会出现我发起、别人负责的任务 | 统一导航文案与列表范围，区分待回复、待确认、我的待办、我发起；不把每次回复包装成拍板 |
| 3 | 群里一个 Agent 生成时，普通人也不能继续发消息 | 群聊消息与 Agent 运行分别处理；谁触发、谁可停止、回复引用哪次问题，以及新增成员时的可见范围 |
| 4 | 聊天缺少自然结束动作；承接任务不能替代结束交流 | 同窗结束入口、会话内摘要、可忽略的待办建议、重新接续；无任务也可收尾，不弹倒计时接受窗 |
| 5 | “定时”目前是到点才送达，容易被误解为处理期限 | 转交区的立即/加急/截止前处理关系，拒绝/延期/撤回及送达反馈；加急规则仍需明确 |
| 6 | 指定资料、允许 Agent 使用、允许同事看原文容易混淆 | 一张共享范围状态图：本人、指定成员、团队；移动/引用/共享的结果，撤权和失效引用的呈现 |
| 7 | 工作进度、可见范围、是否已确认容易被一个状态标签混用 | 文件/结论状态：进行中、已确认版本、更新时间及来源；确认放在责任人自己的工作步骤里 |
| 8 | 群成员目前可加入，但无法退出或移除；手机空间有限 | 成员栏、加入/退出/移除事件、群主权限与历史可见性；主要动作在窄屏和键盘下均可达 |
| 9 | 会议和任务推荐还只有目标设计，尚未定义完整运行状态 | 同步会简报、决策会名单、会议内聊天、会后摘要；任务候选 1–3 人、推荐依据、分配后的来源与状态 |
| 10 | 普通消息视觉已改善，但重型列表和长文体验仍不一致 | 长文宽度、时间分组、列表密度、未读分隔、复制/引用入口、右栏调宽及空态/错误态；维持 Tutti 语义配色，不重新换设计系统 |

“找本人须先完整回答一次”和“不做倒计时弹窗”已由 JC 确认并实现。后续 UI 评审沿用该基线，不再次将提前绕过 Agent 当作默认备选。

| 里程碑 | 估算 | 交付范围 | 前置与退出条件 |

M1–M4 合计约 26–38 个工作日；加约 20% 验收与返工缓冲，按上述产能约 6–9 周。M5 的试点工期不包含完整桌面端、跨平台签名更新、企业多租户和收费系统，这些在试点后分别估工。

主开发的关键路径是：通知与稳定运行 → 聊天收尾 → 持续资料 → 会议/分配。产品设计可提前梳理下一阶段，但在单人开发前提下不把后端工作虚列为并行。每个阶段验收失败先修复，不用后续新功能抵消失败。

## 哪些决定会影响排期？

仅保留会改变流程的待定项，不要求 JC 此刻一次回答全部问题。

- D1/D2：真人通道结束后如何恢复 Agent 接待；有待办、无待办和忽略建议时，摘要何时进入什么范围的记忆。进入 M2 前明确，基本通知和部署不依赖这项决定。
- D3：谁可以在什么范围直接给别人分配任务。进入 M4 的分配实现前明确；当前本人承接和任务完成继续可用。
- D5：加急如何提醒、接收者专注期如何处理、无人回应怎么办。已排除倒计时弹窗；未决部分只影响加急与集中处理，不阻塞基础未读。
- D6：哪些本人动作代表采用某个结论，以及确认如何绑定版本。进入 M3 前明确；文件解析和基础版本存储可先设计。

资源或决策未到位时，主开发先做无依赖工作包并重新估算；需要决定产品取舍时交由 JC/产品负责人，不擅自改动已经确认的 Agent 先答规则。每个里程碑完成后用同一张清单更新状态、验证证据和剩余工期。
