# Tutti 复用与当日 MVP 收口

> 2026-09-05 16:03（北京时间）评估快照。依据：JC 提供的会议转述、当前 Accord 源码与本轮隔离测试、Tutti 官方版本说明。本文为实施建议；不代表 JC 已批准新的范围，也不代表下列待验收能力已完成。比赛截止：2026-09-06 12:00（UTC+8），提交完整代码、PPT 等。

## 1. 判断

今天有机会完成可操作的双人异步探索 MVP，建议继续现有 Accord，复用已经接入的 Tutti UI。不能承诺今天完成 Tutti 级桌面宿主、Claude Code / Codex 历史自动接入、多用户本地工具执行与跨设备授权。

决定能否交付的关键是前端接线与双账号、双机验收。当前已有后端工作流，所以不是从零开发；但测试通过也不等于现场能用。

## 2. 对会议说法的修正

| 会议中的判断 | 建议采用的判断 |
| --- | --- |
| 要实现协作，必须做一个安装在电脑上的 App | Web 也能实现账号、个人会话、成果共享、集中讨论和任务交接。自动读取本地工具、后台执行本地任务时才需要本地连接器或桌面宿主。 |
| 共享上下文意味着可以操控别人的电脑 | 可以只共享本人选定的摘要、资料、成果版本。访问这些数据不要求远程桌面、Shell 或整盘访问。 |
| 读取聊天记录就能接上原来的 Agent | 历史导入、继续原会话、执行工具是不同能力，各需适配和验证。读取文本不等于恢复原进程、工具权限和运行环境。 |
| 三权隔离主要让方案看起来合理 | 权限必须进入服务端数据查询、模型输入和执行入口；界面上的权限标签不能替代校验。 |
| 今天肯定做不出来 | 全量桌面协作平台无法做出可靠承诺；已有基础上的双人工作流可以争取，按验收结果决定演示范围。 |
| 做不出来也可以讲 | 可以讲清后续规划；演示、已完成能力、设计方案和未验证推测须分开。不要宣称已实现自动导入或远程执行。 |

## 3. Tutti 具体复用到哪层

[官方 README 的版本表](https://github.com/tutti-os/tutti#two-versions-of-tutti) 将多人协作、与他人 Agent 协作、借用 Agent、跨设备与免部署分享列在 Tutti · VM；开源版本支持已有 Agent 接入与本人的多 Agent 使用。不能把下载开源仓库等同于获得完整多人控制平面。

| 复用路径 | 对 Accord 的价值 | 当日建议 |
| --- | --- | --- |
| Tutti UI 与工作台布局 | 复用组件和交互基础，保留自己的工作流 | 已采用，继续 |
| 给现有 Web 加 Electron 外壳 | 获得桌面窗口和后续本地接入位置 | 仅在比赛确有桌面要求、核心验收完成后评估；外壳不会自动带来本地 Agent 能力 |
| 整体 fork Tutti 宿主并迁入 Accord 业务 | 可研究现成 Agent 生命周期、配置与工具接口 | 今天不切换主工程；会引入 Go 服务、Electron 打包、配套工具和业务适配 |
| 直接把 Tutti · VM 的多人能力当成可复用开源功能 | 缺少已经验证的代码与运行依据 | 不作为截止前依赖 |

本地参考版本：`404a084f7780c475212f80d6563964c4bd7d8324`。桌面入口 `tutti/apps/desktop/package.json` 包含 Electron 及 `tuttid`、CLI、browser-mcp、Claude sidecar 等打包资源。整体 fork 的判断来自源码依赖与缺少集成验收，并非量化工时测量。组件来源继续记入仓库第三方记录。

## 5. 今天的最小成品与 UI

推荐演示一个课题、两个人、每人一个 Agent、一轮公开和一次交接：

1. 发起人在工作区创建课题，填目标、参与者和截止时间。
2. 每人在自己的工作线与 Agent 探索；共享共同题目，默认不共享个人过程。其他人只看阶段状态。
3. 点击“提交方案”，预览将公开的结论、依据、附件和版本，再提交。提交后显示等待统一公开，不把原始聊天自动塞入团队上下文。
4. 发起人点击“开始汇总”，公开本轮已提交版本。用并排方案卡比较，不用混合聊天记录代替方案。
5. 进入新的评审会话，Agent 使用本轮公开材料帮助比较；发起人确认决策。
6. 向选定成员交接决策与下一步，对方明确接受后进入任务。

在现有工作台中加入课题筛选、个人探索会话、提交预览和汇总区。顶端持续显示阶段，主按钮随阶段变化。首版按钮即可完成全过程；拖动是便利入口，必须复用相同权限与提交逻辑，不成为唯一入口。

主要代码位置：`apps/web/src/app/App.tsx` 负责当前视图接入，`features/workspace/Sidebar.tsx` 提供入口，课题视图负责阶段与动作，`shared/api.ts` 对齐接口。后端复用 `topics.py`、`context.py`、`handoffs.py`，不在前端拼出绕过服务端的共享规则。更细契约见 [007 实施计划](2026-09-05-007-独立探索与集中收束工作流-实施计划.md) 与 [010 设计](2026-09-05-010-会话拖放与模块化上下文-设计文档.md)。

今天先不把多种本地 Agent 适配、自动扫描全部历史、远程终端、任意目录互访、桌面签名发布、音视频会议加入必交范围。主动拉会可先在产品方案中定义为“根据分歧与阻塞建议讨论议题、参会人和材料，由人确认”，未实现时明确标作规划，不演成已经自动召开。

## 6. 共享架构和权限

最小链路是：A 的个人探索 → A 选择发布的成果版本 → Accord 按参与者校验 → B 的 Agent 读取获准成果 → B 决定下一步。两台电脑不需要互相开放磁盘或远程控制。

未来如需本地执行：A 发出任务请求 → B 的连接器接收任务 → 检查 B 授权的目录、工具、有效期与任务范围 → 在 B 本机执行 → 回传选定结果。连接器可主动连接服务端，不要求 A 直接连接 B 的电脑。此为后续架构建议，未在当前 MVP 实现。

三类权限分别是：读取哪些资料，运行哪些工具，以及将哪些成果分享给谁。当前 MVP 只开放获准资料读取和明确发布；不暴露远程工具执行。已有测试是部分边界证据，不能说完成了完整桌面安全验证。
