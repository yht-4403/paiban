# 团队工作状态与可见权限

> 2026-09-05。依据：JC 提出的工作状态、聊天、会议、进度、优先级和权限需求，以及进一步降低使用心智的要求；参考所附 Codex 界面中的搜索、通知入口与侧栏分组。本文保留初始设计，首批执行结果见文末本轮交付状态；自动活动共享默认关闭。截图只用于理解界面结构，不上传其中其他项目与私人任务内容。

## 设计结论与当前事实

Accord 的日常体验围绕“一件工作持续推进”组织：用户表达目标，系统保留上下文与真实进展，需要协作时分享一张工作卡，需要决定时在原处处理。首页围绕“需要你、进行中、最近完成”呈现同一批工作；同事忙闲、Agent 细节和共享范围按需查看。团队动态作为已有工作列表的筛选视图，通知铃铛作为同一事件集合的入口，不要求用户分别维护多个中心。

延续 Tutti 的组件、尺寸和工作台布局，参考截图中搜索、通知与优先分组的组织方式。截图不能证明 Codex 在自动识别同事状态，也不能证明其中“优先级”分组具有任务紧急度语义。

| 能力 | 当前源码事实 | 本设计新增内容 |
| --- | --- | --- |
| 人的工作状态 | `window=open/closed` 由本人手动设置，显示“可协作 / 专注中”；没有过期时间与活动检测 | 区分本人偏好、Accord 内活动信号和授权的外部状态 |
| Agent 状态 | 真实记录排队、生成、完成、错误、停止；前端轮询读取 | 在授权工作列表显示这些状态，后续接真实执行步骤 |
| 当前对话 | 自己发起的会话可见；问同事 Agent 的内容，显式转交前不向同事本人开放 | 另行发布工作标题 / 摘要；完整会话单独授权 |
| 任务进度 | 本人确认后产生待办，状态只有未完成 / 已完成 | 进行中、受阻、待确认、截止时间、优先级和步骤证据 |
| 搜索和通知 | 当前只有可见会话的标题搜索、“待我拍板”列表 | 权限过滤的统一搜索、个人通知中心、关注与已读状态 |
| 会议 | 未接入实际会议状态、日历忙闲或会议内容 | 先手动声明；外部信号接通并验收后再自动更新 |

当前“专注中”也不等于已经具备完整的勿扰投递规则。当前真实实现与验证以 [006 验收](2026-09-05-006-真实工作空间与模型接入-验收记录.md) 为准。

## 用户目标与关键场景

主要服务需要跨人协作的项目成员：希望先自行取得进展信息，在必要时找到能作决定的人，同时保留自己探索和试错的空间。项目协调者是次要角色，需要发现阻塞与收束时机；不因协调身份取得私人过程。以上是依据 JC 需求和现有资料形成的假设型画像，尚无访谈或使用数据验证。

当前成员只能看到手动状态和自己的协作，容易再次发消息询问进展。未来主路径是：在当前工作中提出目标或问题 → 系统继续处理并显示真实进展 → 需要同事时展示接收者和待分享的工作卡 → 本人点击发送 → 在同一张卡中取得答复或作出决定。发送者与接收者的列表、提醒和详情指向同一事项，不要求另外建任务、填进度或到通知中心再处理一次。已经共享的客观状态在约定范围内自动同步。

另一个场景是独立探索：成员可以让主持人知道“探索中 / 已提交 / 需要帮助”，同时保留题目细节、路线、早期答案和私人对话。团队动态必须遵循 [007 独立探索与集中收束](2026-09-05-007-独立探索与集中收束工作流-设计文档.md) 的公开时点，不能提前从摘要、标题或通知泄露方案。

桌面 Web 仍是长期驻留的工作台；状态提示在后台安静更新，需要本人决策时才进入通知。手机优先呈现待处理事项与共享进度，不压缩整个桌面侧栏。业务价值通过实际减少的追问、错误打扰和漏处理来验证，本轮不编造改善比例。

## 降低使用心智的默认交互

用户日常只需知道三件事：当前在推进什么、下一步是否需要自己、哪些内容已交给谁。Run、事件、任务关系、来源权限仍由系统准确管理，不成为启动工作前必须填写的配置。

| 原本需要用户操心 | 收敛后的行为 | 保留的控制 |
| --- | --- | --- |
| 先选择会话、任务、Agent 或动态入口 | 从工作台直接输入；标题先自动拟定，继续围绕同一件事对话 | 可以改标题、停止处理、另起一件工作；系统不强行合并无关事项 |
| 维护在线、忙碌和生成状态 | 真实业务事件自动形成进度；联系同事时再查看其已共享的忙闲 | 自动活动共享仍由本人开启，勿扰可一键覆盖；未知不冒充空闲 |
| 再写一份进度更新 | 已共享卡上的步骤、产物、待确认结果自动更新 | 私人内容生成的摘要先预览，点“发给某人”才发布 |
| 学会 Agent 与真人的路由 | 选择同事后，系统先走获准的 Agent 协助流程 | 行内明确“由助理处理，本人尚未收到”；需要打扰时点“请本人确认” |
| 每条消息设置权限档位 | 私人工作默认仅自己；发送工作卡时直接显示实际接收者与内容 | 同一授权范围内不重复询问；加入新接收者或分享原文时明确处理 |
| 同时整理优先级、通知与待办 | 待本人决定的事项突出，其余按已知截止、依赖与个人置顶排列 | 显示简短排序理由；个人可调整，项目优先级不被 AI 静默修改 |

### 一张卡贯穿协作

工作卡不是另一张必须填写的表。它从当前事情中带出目标、真实进度、下一步和必要产物，缺少的关键内容在对话中补齐。卡内直接提供当前适用的操作，例如补充信息、请本人确认、接受任务、发布成果；不固定摆满所有按钮。

首页“需要你”只收纳需要本人决定或输入的事项。一般更新安静地留在工作下；铃铛可访问完整通知记录，不形成第二套审批队列。处理后各处同步，不再要求另勾待办或另标通知完成。用户关闭提示、读过消息、说“收到”，都不被解释为接受任务或批准共享。

找同事时默认由其 Agent 在权限范围内协助，不要求发送者先判断对方是否方便。状态只辅助是否与何时联系本人，不能替发送者自动升级为真人通知。缺少真实资料或 Agent 处理失败时，说明缺项并给出下一步，不为了保持顺滑编造进展。

### 把共享选择放到发送动作里

第一版以“私人对话 + 明确分享的工作卡”为默认路径，完整历史与持续共享放在详细选项。卡上常驻接收者或“仅自己”的文字，点击可以查看具体范围；颜色和图标不承担唯一提示。

“发给某人”这一动作同时完成确认和发送：按钮旁已经展示接收者、摘要、产物，以及“分享这张工作卡，私人聊天保持私有”的后果，不再先填权限表、再经过相同内容的确认弹窗。发送成功有回执；失败保留待发内容，不显示已共享。修改摘要或更换接收者后，预览随之更新。

成员接受一件工作时，可在同一张卡上同意向这些接收者持续同步该工作的客观进度，避免每次更新重复授权。该授权只覆盖列明的字段和接收者，不覆盖私人聊天的新摘要，也不延伸到其他工作。新增成员、扩大共享字段或附上私人原文仍是新的分享动作；已知默认值不能代替新增授权。

初次使用直接进入自己的工作区，既不要求先配置角色矩阵，也不要求先连接日历或打开活动共享。只有确实用到某项外部能力时才提供连接入口；拒绝连接不阻断站内协作。高级选项保留在详情里，常用的下一步、当前进度、接收者和停止操作保持可见。

这次简化的可验证目标是减少重复输入和跨页面操作，尚未验证效率提升。先观察成员能否在无需讲解 Agent、Run 或授权模型的情况下发起协作、知道谁能看、完成一次本人决定，再判断是否需要增加独立的团队动态页面。

### 拖放与上下文的直接操作

文件夹、当前资料区和参与者区域承担不同的落点：聊天归档与已有资料绑定直接完成；私人内容落入分享区域时就地形成待发卡，发送动作同时完成确认。以插入线、资料标签和实际接收者表达结果，常规操作不弹模态确认，也不持续展示解释文案。文件夹默认资料、模块组合、移动后上下文及只读工具契约见 [010 会话拖放与模块化上下文](2026-09-05-010-会话拖放与模块化上下文-设计文档.md)。

## 状态来源与表达

### 人、Agent 和工作分别建模

| 维度 | 建议展示 | 可信来源与限制 |
| --- | --- | --- |
| 联系偏好 | 可联系、专注中、勿扰至指定时间 | 本人设置；这是偏好，不能证明本人在线 |
| Accord 内活动 | 最近在 Accord 活动、正在参与此共享讨论、状态未知 | 经本人开启的应用内信号；打开网页不等于持续工作 |
| Agent 运行 | 排队中、正在生成、等待确认、失败、已停止、完成 | 服务端 Run / 审批事件；可与本人离线同时发生 |
| 任务推进 | 未开始、进行中、受阻、待确认、已完成、已取消 | 负责人或已授权工具的真实业务事件；完成需满足任务验收 |
| 会议 | 本人设置的会议中、日历显示忙碌、最近已入会 | 来源分别标注；会议主题、参会者和内容另行授权 |

“正在参与此共享讨论”仅在该讨论的授权参与者视图中显示。输入提示只传短期布尔状态，不传草稿、按键、鼠标轨迹或正在看的其他窗口；查看页面不自动广播“已读”。面向团队的泛化活动标签也需要本人开启。

### 信号生命周期与冲突

下列数值是第一版工程建议，尚未实测，需通过验收确定：

- 可见页面每 30 秒发送一次会话绑定的心跳，结合本地近期交互生成粗粒度活动信号；不上传具体操作内容。90 秒没有有效心跳，自动状态降为“状态未知”；5 分钟没有交互，不再显示“最近活动”。后台标签页、断网和电脑休眠都不能被解释为“不工作”。
- 输入提示建议 5 秒失效，仅向当前有权阅读该讨论的人返回。多端按有效会话聚合，关闭一个标签页不把其他设备标为离线。
- 本人设置的勿扰优先决定提醒方式；专注或会议手动声明可选 30 分钟、1 小时或自定义结束时间。自动信号不覆盖本人偏好；声明到期后恢复当前有效规则，没有信号时显示未知。
- 每条自动状态带来源、最近确认时间和有效期。成员可查看自身信号、纠正状态、暂停自动共享；对外只显示已授权粒度。
- 活动心跳只维护当前短期状态，过期清理；不把原始心跳、输入事件累积为工时或效率排名。授权与业务动作记录审计，正文和草稿不进入状态日志。

### 外部聊天和会议的接入边界

飞书官方 CLI 的 `+freebusy` 提供主日历忙闲与 RSVP 信息，因此可以用于展示“日历显示忙碌”。据其数据语义，不能据此断言本人正在参会，会议主题也不需要进入状态投影。[官方日历说明](https://github.com/larksuite/cli/blob/main/skills/lark-calendar/SKILL.md)

官方会议事件说明列有当前授权用户参与会议的开始、入会、结束事件，需要用户身份与会议事件权限。该目录未给出“本人提前离会”的对应事件，会议结束与个人离会也不是同一个事实。因此，仅拿到入会事件时显示“最近已入会”和确认时间；持续显示“会议中”之前，需要进一步验证当前参会状态的读取能力、退出恢复与事件遗漏补偿。[官方会议事件说明](https://github.com/larksuite/cli/blob/main/skills/lark-event/references/lark-event-vc.md)

接入必须绑定每位成员自己的外部身份、本人选择的状态用途与团队可见范围。JC 本机 CLI 的登录不能代表所有同事同意共享。外部消息正文、聊天窗口标题、屏幕和录音不属于忙闲识别的必要输入；本轮不启动订阅，也不读取这些内容。Accord 外正在聊什么，需要另一个明确授权的内容连接器，不能用“识别状态”一并取得。

## 工作台布局与交互

| 位置 | 内容 | 操作与反馈 |
| --- | --- | --- |
| 左上角搜索 | 我有权访问的工作、会话、成果和人员 | 搜索前由服务端过滤；标题、片段与结果数量都不能暴露私有对象 |
| 左上角通知铃铛 | 与工作台共用的事项与通知记录 | 显示未读数；处理同一事项后同步；标已读不等于批准或完成 |
| 侧栏工作列表 | 最近工作与个人置顶，保留稳定入口 | 提供置顶和取消置顶；不增加必须维护的“优先级分组” |
| 工作台主区 | 需要你、进行中、最近完成；可切换我参与 / 团队共享的筛选 | 不重复创建事项；正常进展安静更新，需要决定时直接操作 |
| 工作列表行 | 工作标题、真实阶段、下一步或阻塞、必要时的优先级与更新时间 | 默认紧凑行；成员状态在相关头像与找人时按需展开，Agent 详细轨迹进入详情 |
| 工作详情 | 摘要、依据与产物、下一步、等待谁、实际接收者 | 当前适用的动作就地出现；完整会话与高级共享选项按权限展开 |
| 我的状态与共享设置 | 手动状态、自动来源、共享对象、到期时间 | 固定提供“以同事视角预览”；可立即停止共享 |

侧栏不罗列全员所有聊天。它保留个人工作的稳定入口；团队共享是同一工作列表的视图，通知也回到原事项处理。动态更新不抢输入焦点、不重排用户正在点击的行；有新项时提示“有更新”，由人刷新排序。

继续采用 Tutti UI System 的中性色、字阶、列表选中态、图标和面板规则。头像旁的标记表示人的状态，工作行内的标记表示 Agent；文字和图标共同表达含义，不能只靠绿点。搜索与铃铛有可访问名称、键盘入口，面板支持 Esc 返回和焦点恢复；手机不依赖悬停才能看状态来源。

空状态分别说明“尚未共享状态”“暂无可见工作”“没有待处理事项”；断网显示最后更新时间；无权限的对象不返回标题。没有真实成员、任务或信号时不填预置内容。

## 进度、优先级和通知规则

进度优先显示“当前步骤、已完成步骤、阻塞原因、下一步与更新时间”。仅在步骤集合或工作量分母明确时显示完成数；按步骤计算时明确写“步骤完成度”，不同步骤不必等量。没有可靠分母就不画百分比；模型还在输出多少字也不能换算成项目完成率。任务步骤变化时记录分母变化。

Agent 回答完成，只代表该次生成结束。它整理出的计划、预计时间和风险是建议；任务完成需要负责人确认，或预先授权且有验收依据的业务动作。重试生成不重复创建业务任务。

项目任务建议支持“紧急 / 高 / 普通 / 低 / 未设置”以及截止时间、排序理由。负责人可更新自己的任务；项目协调者若具备任务管理权限可调整项目优先级并留下变更记录。其他人可以建议紧急度，AI 可以依据有权查看的截止、依赖与阻塞提出建议；不能从私人聊天推断后自动修改。个人置顶独立保存，不影响其他人的排序。

通知只覆盖明确交给我的事项、授权讨论中提到我、我关注的任务受阻 / 完成 / 到期。普通心跳、每个生成片段和每次输入不产生通知。按事件与接收者去重，重连不重复提醒；勿扰期间留在收件箱，外部推送按本人设置延后。标成“紧急”也不能自动绕过勿扰；是否允许例外由接收人预先设置。

系统推送和锁屏默认只说“有一条待处理协作”；标题、摘要的外部预览另行开启。每次查看通知重新鉴权，资源撤权后不能继续从旧通知读到内容。只获准知道“有事待处理”的接收者不能收到私有会话标题或片段。

## 内容可见范围与权限

建议把权限分成“对象范围 × 可见内容 × 可做动作 × 有效期”，界面提供几种容易理解的选择，不要求成员填写复杂矩阵。以下是设计默认值，不表示已调整现有账号权限。

| 查看者 | 人的状态 | 工作标题与进度 | 工作摘要 | 完整聊天、附件 |
| --- | --- | --- | --- | --- |
| 本人 | 自己的状态来源与共享预览 | 自己有权限的工作 | 自己有权限的内容 | 按本人原有资源权限 |
| 普通同事 | 本人明确共享的忙闲；新增自动活动默认关闭 | 仅已向其发布的工作 | 仅已发布的摘要版本 | 默认不可见 |
| 项目协作者 / 主持人 | 同上，不因角色扩大 | 该项目中已共享的任务；探索期遵循轮次规则 | 已向当前轮次 / 项目发布的摘要 | 需另外取得会话与附件权限 |
| 已授权会话参与者 | 依照人的共享设置 | 该会话和可见关联任务 | 可见消息范围内的摘要 | 仅授权的历史区间 / 后续消息；附件独立校验 |
| 团队管理员 | 管理账号、集成和团队策略 | 管理身份本身不增加业务内容读取权 | 不自动取得 | 不自动取得 |

会话可读、可评论、可编辑、可执行任务、可分享与可管理权限分别判断。一个人能看材料，不代表他有权把它转给更多人；获准看摘要，也不等于获准读原文或让 Agent 以本人身份执行动作。

关键边界：A 问 B 的 Agent 时，运行归于本次发起者 A，不能把它自动发布成“B 正在工作”或“B 正与 A 讨论某主题”。B 的 Agent 名字不是 B 对这段内容的访问授权。团队级运行数量、名称与更新时间也只能来自当前查看者可见的工作，不能用隐藏计数透露私人活动。

### 分享工作而保留私人过程

第一版在当前工作中提供待分享卡片：系统带出可编辑的标题、摘要、进度、下一步和允许分享的引用，接收对象从当前明确的协作意图带出；不明确时再由本人选择。预览与“发给某人”放在同一处，发送后形成独立版本。默认不附完整历史，不把未来消息自动纳入共享。

已共享任务的客观状态可以在原有受众内自动刷新；私人聊天生成的新摘要先成为草稿，再由本人发布。第一版不承诺 AI 可以持续读取私人聊天并自动安全地公开摘要。敏感主题在摘要中改了措辞也不自然获得分享权。

需要共享会话时，单独选择“指定历史快照”或“允许后续更新”，并展示消息起止、接收者、有效期和涉及的附件。新增参与者、扩大受众或公开多人私人消息时，需要已有分享授权或受影响内容所有者的同意；不能只凭发起人的单次操作转授权其他人的材料。

摘要默认继承来源限制。只有拥有相应分享权的人明确批准，才能发布指定摘要到新的范围；记录发布版本、来源和发布者。多人摘要的可见范围受所有相关来源约束，模型不是授权决策者。发散期未公开的方案不得通过团队动态、Agent 回答或通知提前流出。

### 撤销与实际保障范围

撤销后，服务端立即拒绝新的读取、搜索、推送和模型上下文构建，并使相关缓存 / 订阅失效。已打开页面在正常联网时目标 5 秒内移除撤权内容；失败时标明无法刷新，不把旧权限当新授权。已经被阅读、截图或下载的内容无法保证收回。

若生成过程中来源被撤权，停止后续使用并在发布前重新检查；不能把已发送给模型供应商的请求说成从未发生。审计保留授权、撤销、发布和业务动作的最小记录，不把私人正文复制进日志。

上述属于应用层权限。目前 SQLite 与服务端运行环境没有端到端加密隔离；能直接控制数据库或宿主机的运维人员是另一层信任边界。不能把“团队管理员不能通过产品读私聊”宣传成“任何系统管理员在任何情况下都读不到”。

## 后端落点与实施顺序

在现有 FastAPI / SQLite / HTTP 轮询上逐步增加，不先引入新的实时框架。

| 对象 | 最小职责 |
| --- | --- |
| PresencePreference / PresenceSession | 本人联系偏好、共享范围、有效期；各登录会话的短期活动信号，服务端绑定身份 |
| WorkUpdate | 对外工作标题、摘要版本、来源、发布者和发布时间，与私人会话正文分开存放 |
| TaskProgress | 任务阶段、步骤依据、阻塞、截止、优先级、负责人和版本 |
| ResourceGrant | 对象、接收者、可见字段 / 消息范围、动作、有效期、撤销状态与授权版本 |
| ActivityEvent / Notification | 真实业务事件、来源、对象版本；按有权接收的人生成通知和已读状态 |
| ExternalConnection | 成员身份绑定、允许用途、来源权限、连接健康度和撤销状态 |

数据路径：可信业务事件 / 本人授权的信号 → 归一化当前状态 → 按查看者权限生成返回内容 → 列表、详情、搜索、通知、Agent 上下文。先鉴权再聚合；不得把所有人的消息发到浏览器后隐藏。

前端统一工作卡的标识及关联关系，让会话、请求、任务、更新和通知都回到同一件事；底层保留各自状态和权限，不能因界面合并而把“已读、已接受、已完成、已共享”合成一个状态。首版优先复用现有会话和任务关联；新的工作对象是否需要独立表，在接口实现时确定。

建议接口：`POST /api/presence/heartbeat`、`POST /api/profile/presence`、`GET /api/activity`、`POST /api/work-updates`、`POST /api/grants/{id}/revoke`、`GET /api/notifications`、`POST /api/notifications/{id}/read`。这是待实现契约；写操作沿用 operation_id 幂等，业务编辑增加 expected_version 冲突检查，事件使用 event_id 去重。客户端不能上报别人的身份或自行指定接收者绕过服务端权限。

当前 artifacts 全部作为团队共享资料读取，不能把新的私人摘要草稿、未公开方案或权限不明的会议内容放入这个集合后只隐藏前端。须先增加资料范围与读取校验，覆盖 API、搜索、导出、通知与模型上下文。会话目前用转交状态决定接收者可见性；细粒度分享需显式 Grant，不能继续用单一 status 同时承担工作状态和全部权限。

| 次序 | 交付结果 | 完成依据 |
| --- | --- | --- |
| 第一批：权限与状态 | 明确共享预览；保留现有手动状态；新增本人可开关的 Accord 活动、授权 Run 状态与失效处理 | 私有元数据不泄露，未知状态不冒充工作 / 空闲，撤权生效 |
| 第二批：协作可见性 | 同一工作台中的共享卡、就地确认、进度与优先排序；团队共享筛选和同源通知入口 | 两人真实发布 / 查看 / 处理，第三人只见其授权范围；无需重复填写或跨中心处理 |
| 第三批：外部会议 | 成员各自连接飞书、忙闲和已验证的参会状态 | 验证入会、提前离会、会议结束、取消授权、丢事件与重连；再启用自动“会议中” |
| 后续：共享讨论扩展 | 指定历史 / 后续更新、会议纪要、实时工具步骤 | 消息与附件的分享权完整，调用前后均能校验，产物与进度有真实依据 |

前两批形成第一个完整可用版本；第一批单独上线时不摆放第二批尚不可用的按钮。UI 新增范围使用 Tutti 现有组件，完整聊天共享和外部会议不以虚构数据占位。团队可用部署仍依赖 006 中的上线工作，不由本设计自动完成。

## 验收标准与开放问题

以下均为待执行标准，本轮没有运行这些新功能的测试：

1. A 在私人会话问 B 的 Agent，B 和 C 通过活动、搜索、计数、通知或 Agent 追问均不能获得标题、消息或运行细节；A 看见真实生成状态。
2. 本人关闭网页但 Agent 仍运行时，两种状态独立显示；断网 / 休眠 90 秒后不继续显示有效活动；输入提示过期消失，且其他会话不收到输入事件。
3. A 发布一份摘要给 B，C 看不到；B 能看摘要但不能据此打开原始聊天或无权附件；私人会话的新消息不会自动公开。
4. 发散轮次收束前，主持人只看到约定进度；已提交方案不会从动态摘要、搜索或汇总模型提前出现。
5. 撤权阻断后续 API、搜索、通知、订阅和模型上下文；正在生成的发布前再鉴权。移出团队后旧会话不能继续上报心跳或读取团队内容。
6. Agent 生成结束不自动完成业务任务；没有步骤分母时无百分比；优先级修改有权限与版本校验，个人置顶不改变团队任务。
7. 重复与乱序事件不回退新状态、不重复提醒；通知标已读不代替审批，勿扰不被“紧急”标签无条件穿透。
8. 日历忙碌仅显示其来源；仅收到入会事件但缺少持续参会证据时，不声称仍在会议；手动结束、连接失效与授权撤销都有恢复路径。
9. 键盘可打开、关闭搜索与通知并返回原焦点；移动端可查看来源和更改共享范围；刷新失败、无权限、空列表都有准确反馈。
10. 首次使用无需配置活动来源、日历或权限矩阵即可开始私人工作；同一协作只需在发送处检查一次实际接收者与内容，不再经过重复确认弹窗。
11. 接受任务、补充信息或作出决定后，卡片、工作台和通知关联到同一结果；关闭提示、已读或普通聊天回复不改变承诺与授权。一个真实进度事件不要求成员再次手填更新。
12. 无指导观察成员完成发起、分享和处理，记录跨页面次数、重复输入、接收者判断错误与所需解释；初版目标是没有重复录入、没有误共享，实际结果待测，不用自动化次数替代使用体验。

尚需真实团队试用决定：成员愿意共享的活动粒度、发散期是否仅公开提交状态、需要哪些通知例外、共享摘要是否足以替代追问。当前建议按最少默认公开、本人可选范围推进；这些设置在实现中可调整，不把尚未讨论的选项写成已获团队同意。

本轮已完成源码核对、官方接口文档查阅与可实施设计；没有修改运行服务、账号权限、密钥或活动采集配置。后续验收需在隔离数据上覆盖上述多人边界，再使用成员明确提供的真实内容验证协作。

## 统一对话接续：实现与验收

2026-09-05，JC 要求按客服转人工的体验，让 Agent、本人与确认动作在同一个对话和输入框里接续。本节参考当天已下载的[堡天 Demo 源码与产品需求](https://my.feishu.cn/drive/folder/QlhzfyXL5lWfy1daiiyczfg1nIc)：其 renderChat / doSend 已共用会话与输入区域，但 openFind 仍使用弹窗。Accord 采用连续对话方式，并将找本人和承担任务收进主输入框；此前关于自动工作状态、会议识别与完整权限分层的内容仍属待实现设计。

| 环节 | 当前实际行为 |
| --- | --- |
| Agent 先接待 | 标明对方姓名与 Agent 代答；提问和回答保留在当前消息流 |
| 请本人接入 | 点击后在原输入框补充说明，附近显示接收者、消息范围和现在 / 定时发送；没有额外对话框 |
| 取消或发送失败 | 保留编辑内容，取消后恢复原聊天草稿；定时时间无效时就地提示，不产生转交 |
| 本人回复与确认 | 本人第一次回复产生接续记录；原输入框可填写确认结论并编辑任务名称，再明确承担 |
| 继续推进 | 任务卡留在消息流，确认后仍可回复；负责人能在卡内完成或重新打开任务 |

同一会话不意味着隐去访问边界：转交前对方和第三人不能读取；发送明确开放本段已发送记录。接入前未发送的私人草稿与真人会话草稿分开保存，不会自动成为发给本人的内容。本人回复不会被误记为承担任务；确认后的普通聊天不重新调用 Agent、不重复生成任务，也不自动标记任务完成。

实现主要位于 ConversationInput.tsx、Conversation.tsx 和 Composer.tsx；主输入框复用原有资料绑定与上下文能力，任务卡调用既有的负责人校验接口。后端允许已确认会话继续接受双方消息，保留已确认状态；新增针对继续回复、无重复任务、无额外模型调用和第三人拒绝的行为测试。初次加载结束后恢复消息区到最新位置，避免手机刷新后停在旧消息。

验证：当前 34 项后端测试通过；类型检查、构建和 UI 边界检查通过。隔离账号浏览器验证了单一输入框、无转交 / 确认弹窗、取消恢复草稿、定时校验、转交前后权限、本人回复、原地确认、确认后继续聊天与任务卡完成，以及 1440 / 768 / 390 宽度和亮暗主题。使用真实 deepseek-v4-pro，两个验收请求分别回报 901 和 920 tokens，共 1821 tokens；第一次浏览器在确认环节关闭，第二次完整流程通过，未把中断那次记录为完整通过。

测试仅使用 .local/unified-conversation 下的隔离数据库与账号，未向真实队友发送消息。截图归档于 screenshots/2026-09-05-统一对话接续，仅作为本地验收附件，本节不上传账号记录、原始响应或模型凭据。此处验证的是浏览器响应式布局，未替代真实手机软键盘与触控验收。
