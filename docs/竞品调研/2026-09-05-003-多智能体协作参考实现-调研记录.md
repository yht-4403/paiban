# 多智能体协作参考实现

> 调研日期：2026-09-05。Tutti 使用本地固定 commit；其他项目依据当日官方仓库和文档，未在本机运行。分类和复用优先级是针对 Accord 的工程判断，不是市场份额排名或全面安全审计。我们的建议见[多人多智能体协作架构](../技术架构/2026-09-05-001-多人多智能体协作架构-设计文档.md)。

## 先给判断

Tutti VM 属于与 Accord 有明显重叠的竞品；Tutti 开源版提供个人多 Agent 工作台参考。AgentTeams 在“人和多个 Agent 共同协作”上很接近，也有公开实现，值得优先研究。OpenClaw / QwenPaw 更适合作为个人 Agent 运行时参考；LangGraph、OpenHands、A2A、MCP 分别解决工作流、执行环境或互通问题，不能都当作完整竞品。

| 项目 | 归类 | 对 Accord 最有用的部分 | 使用判断 |
| --- | --- | --- | --- |
| Tutti / Tutti VM | 竞品、工作台与执行宿主参考 | UI、会话生命周期、配置快照、共享 Agent 的控制边界 | 继续现有 UI 接入；跨人业务控制需自己核查和实现 |
| AgentTeams | 接近的开源协作系统 | Human / Manager / Worker、房间协作、任务产物与运行容器 | 优先读其分层和任务 API；比赛不引入整套基础设施 |
| OpenClaw | 个人 Agent 运行时 | 多 Agent 路由、分开的工作区、跨会话任务、定时触发 | 可做后续适配器；多人私有数据隔离要单独设计 |
| QwenPaw（原 CoPaw） | 个人助手与团队托管参考 | 多渠道、多 Agent、Hub、Agent 协议适配 | 与 OpenClaw 按飞书接入和运行成本比较，尚未做选型验证 |
| Relevance AI Workforce | 商业工作流竞品 | 按动作配置批准、升级找人、待处理中心 | 参考交互和授权颗粒度，非可直接复用的开源底座 |
| LangGraph | 编排框架 | 持久流程、等待人输入与恢复 | 流程复杂后评估；本次简单状态机也可实现 |
| OpenHands SDK | 代码 Agent 的执行参考 | Local / Remote / Docker Workspace 的边界 | 只有需要跑代码或命令时重点研究 |
| A2A / MCP | 协议 | Agent 间任务互通 / 工具资源接入 | 保留适配接口，不取代身份、权限与业务状态 |
| Grok / xAI | 模型与工具调用能力 | 接入模型和远程 MCP | 不能据此认定已经具备 Accord 的多人协作系统 |

## Tutti：可复用什么，哪里尚未证实

本地 commit：`404a084f7780c475212f80d6563964c4bd7d8324`。桌面和 daemon 已启动，但未验证真实模型任务、VM 多人房间及跨用户借用 Agent。

其主要分层可理解为 Electron / React 工作台 → Go tuttid → Agent Host → Provider / 执行进程。源码 `packages/agent/host/lifecycle.go` 中 CreateSession 统一会话创建与运行操作，使用提交记录处理重复请求；`submit_claims.go` 包含接受、拒绝和重放提交结果的处理。值得借鉴的是生命周期和请求身份的统一入口，不是照搬 Go 技术栈。[Host 源码](https://github.com/tutti-os/tutti/blob/404a084f7780c475212f80d6563964c4bd7d8324/packages/agent/host/lifecycle.go)、[提交记录源码](https://github.com/tutti-os/tutti/blob/404a084f7780c475212f80d6563964c4bd7d8324/packages/agent/host/submit_claims.go)

架构文档把 WorkspaceAgent、模型配置、运行快照和自动化规则分开；共享调用由外部控制层负责所有人身份、授权、并发、额度和代理执行，凭据留在所有人侧。独立本地版不包含跨用户目录。这正说明“共享 Agent”需要一套服务端业务，而非复制 Agent 配置即可完成。[架构文档](https://github.com/tutti-os/tutti/blob/404a084f7780c475212f80d6563964c4bd7d8324/docs/architecture/workspace-agents-and-automation.md)

**本次核查修正：**全文搜索 `SharedAgentAccessController` 和 `SharedAgentAccessAuditor`，只在上述架构 Markdown 找到名称，未找到对应 Go 声明或实现。本轮只能把它们列为文档描述的契约，不能说已验证运行时强制执行。也不能凭此断言 VM 没有实现，可能存在外部实现或文档与代码不同步。旧调研中的“有访问控制与审计接口”应按此证据等级理解。

应用到 Accord：Agent 配置和会话分开；历史配置可复现，当前授权仍可撤回；界面显示“可借用”只是状态投影，每次真正读取、执行和发布都要由控制层检查。

## AgentTeams：最值得进一步拆的开源协作实现

官方设计将系统拆为 Go Controller、Manager、独立 Worker 容器及共享基础设施。Matrix 房间承载人和 Agent 的消息时间线；对象存储保存工作文件；Higress 处理模型和工具入口。Worker 可使用不同 Agent 运行时，持久文件与可替换执行进程分开。它同时提供本地容器和 Kubernetes 部署路径。[官方架构](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/design/architecture.md)

这与 Accord 的多人多 Agent 很接近：可以借鉴“协调层负责组织，执行层按角色运行”的分工。不能直接把共享 Matrix 房间当成个人资料隔离；Accord 仍要区分房间成员可见内容和个人 Agent 的私人上下文。对我们的小团队比赛，Matrix、网关、对象存储、容器控制器全套引入的代价偏高。

另一个值得读的入口是项目工作流 API：它提供任务图、人工等待点和产物读取，文档规定读取产物需同时满足任务已声明文件与允许路径范围；不是给前端一个任意存储路径就下载。可借鉴“聊天协调 + 结构化任务与产物”的双层设计。[工作流 API](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/usage/project-workflow-api.md)

本轮只读官方资料，未部署、压测或验证其身份隔离；main 分支会变化，实际引入时需冻结 commit 并核查依赖。

## OpenClaw 与 QwenPaw：适合研究个人侧

OpenClaw 支持为不同 Agent 配置独立工作区和会话状态，并按入口路由；其会话工具提供读取、发送和派生任务等能力。对 Accord 的价值是个人 Agent 内部怎样分工和调度。[多 Agent 文档](https://docs.openclaw.ai/concepts/multi-agent)、[会话工具](https://docs.openclaw.ai/concepts/session-tool)

必须注意其官方信任模型：一个 Gateway 对应一个可信边界，支持互相信任的团队，但不承诺将同一 Gateway 上互不信任的人隔离为独立租户。当前文档还说明跨会话可见范围与 Agent 互调的默认设置较宽。因此不能直接让全员共用一个 Gateway，再以不同 agent_id 宣称个人数据隔离。[安全文档](https://docs.openclaw.ai/gateway/security)

Heartbeat / 定时任务提供唤醒机制，可以借鉴为 Accord 的超时检查；“什么时候值得开会、谁批准、如何避免重复邀请”仍是产品工作流。[Heartbeat](https://docs.openclaw.ai/heartbeat)、[定时任务](https://docs.openclaw.ai/cron-jobs)

原 CoPaw 仓库目前重定向至 QwenPaw，官方 README 展示多 Agent、多渠道及 Hub 方向。它可作为个人助手侧另一个候选，但本轮未验证 Hub 的权限模型和实际接入成本，不把“支持多用户”直接等同于满足 Accord 私人资料边界。[官方仓库](https://github.com/agentscope-ai/QwenPaw)

## 工作流与执行环境参考

Relevance AI Workforce 的官方文档将动作边的策略分为自动执行、必须批准、由 Agent 判断，并有任务中心展示待批准和升级请求。这值得用于 Accord 的待拍板区：用户应能看清动作内容、依据、批准历史。涉及 Accord 强制确认的动作不能交给模型自行判断是否跳过。[批准与升级文档](https://relevanceai.com/docs/build/workforces/workforce-features/approvals-and-escalations)

LangGraph 的 interrupt 与持久化支持等待外部输入后继续工作。它负责流程执行，不会自动建立成员身份、资源 ACL 或责任人的验收动作；恢复时中断节点会从头重跑，外部副作用需要自行处理幂等。[官方 interrupt 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

OpenHands SDK 区分本地和远程 Workspace，并提供 Docker 工作区相关能力。适合研究“代码在哪儿执行、文件怎样进出”；不要将普通本地目录等同于安全隔离环境，也无需为纯问答任务先装代码执行系统。[Workspace API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.workspace)

## Grok bot 应该怎么理解

如果 JC 指 xAI 的 Grok，它可以是 Accord 的模型与工具能力提供方。官方文档有远程 MCP 接入，但模型能调用工具并不等于产品已具备多人的身份、委托、私有工作区、会议状态及批准记录。这些仍由 Accord 的协作层管理。[远程 MCP 文档](https://docs.x.ai/developers/tools/remote-mcp)

如果指某个以 Grok bot 命名的独立开源项目，需要具体仓库才能判断；本轮没有把它擅自认作 OpenClaw。OpenClaw 与 QwenPaw 是另列的个人助手参考。

A2A 与 MCP 可同时使用：前者侧重独立 Agent 之间协作，后者侧重工具和上下文接入。先定义 Accord 内部任务契约，未来通过适配器互通，比比赛前同时实现两套完整协议更合适。[官方关系说明](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)

## 建议研究顺序与差异化

1. Tutti：继续已经授权的工作台接入，并借鉴会话生命周期和提交幂等。
2. AgentTeams：优先看 Controller / Worker 分离、任务图、产物与人工等待点，形成我们后端对象模型。
3. OpenClaw / QwenPaw：等确有本地 Agent 或多渠道需求时，再试接一种运行时，不同时接两套。
4. LangGraph / OpenHands / A2A / MCP：分别在流程复杂、要执行代码、接外部 Agent、接工具时按需引入。

Accord 可以尝试验证的区别是：同事 Agent 先接住请求，只依据获准资料代答；解决不了再带着证据找本人；结论、任务责任和共享产物有明确的人类确认。它是否真正减少打扰，要用代答解决率、升级质量、重复通知数、从请求到确认的时间和越权测试结果说明。不能只以“我们也有多 Agent”作为独有创新。
