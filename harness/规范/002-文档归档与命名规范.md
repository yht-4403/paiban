# 文档归档与命名规范

沿用 JC 在 cv-project 的归档习惯，所有路径适配到 Accord；不继承 cv-project 的业务数据、账户、端口或技术栈。

## 归档位置

| 内容 | 位置 |
| --- | --- |
| 根入口与必要配置 | 仓库根目录 |
| 长期工程规范 | `harness/规范/NNN-规范名称.md` |
| 背景、方案、计划、调研、验收、复盘 | `docs/<中文业务分类>/` |
| 浏览器、UI、调试截图 | 工作区统一的 `screenshots/YYYY-MM-DD-主题/` |
| 原始资料响应、下载缓存、临时脚本 | `.local/`，不提交 Git |
| 正式产品 Logo、图标与测试基准图 | 对应业务资产目录，按需提交 |

`docs/` 按业务分类，默认两层。现有分类为“产品规划”“团队协作”“竞品调研”；有真实内容后再新增。

## 命名格式

```text
docs/<业务分类>/YYYY-MM-DD-NNN-主题名称-文档类型.md
```

- 日期使用北京时间的创建日期；迁移时不知道原日期可用迁移日，并说明来源。
- 每个分类独立编号。创建前先搜索相同主题；同一主题的设计、计划、验收、复盘共用 `NNN`。
- 文件名无空格；主题优先使用中文、数字和短横线。工程固定入口 `README.md`、`AGENTS.md` 等保留惯例。
- 固定文档类型：设计文档、实施计划、接口契约、验收记录、复盘文档、调研记录、问题排查、迁移说明、交接文档、任务清单。
- 示例：`docs/产品规划/2026-09-05-001-项目背景与需求基线-交接文档.md`。
- 不创建“最终版”“最终版2”等并行副本；持续维护现行文档，历史决策用日期和 Git 追踪。

## 索引与证据

- `docs/索引.md` 提供分类和主题入口；新增重要文档后更新索引。
- 仓库内部 Markdown 使用相对链接，方便他人拉取；对 JC 的回复使用绝对路径链接。
- 来源说明优先用首行引用块或简短来源表，记录 URL、日期、文档版本或 commit。
- 区分用户明确决定、原始资料陈述、已验证事实、建议与待确认项。
- 私有原文与接口 JSON 缓存放 `.local/sources/`，保留内容及引用元数据；可提交文档只写任务所需的整理内容，不复制凭据、私人会话或无关资料。
- JC 已授权将 docs 在任务交付时同步到飞书“健城 / Accord”，按 [003-飞书文档同步规范](003-飞书文档同步规范.md) 执行；其余平台、公开权限或消息发送不在这项授权内。

## 截图

统一路径：`/Users/JCProjects/accord/screenshots/YYYY-MM-DD-主题/序号-场景-尺寸.png`。
worktree 和子项目均使用此位置；工具先生成临时图片时，再复制到统一目录。

只提交 `screenshots/README.md`。验证截图可用 `git check-ignore`，不要用全局 `*.png` 或 `*.jpg` 规则误伤正式资产。
文档标明截图为“本地验收附件”；其他协作者拉取仓库不会得到这些附件。

## 迁移与自查

- 迁移现有材料前记录旧路径、目标路径、保留链接与冲突处理；不直接批量移动第三方资料。
- 检查目标文件、分类编号、链接和索引是否一致。
- 确认缓存与截图被忽略，正式资产未被误忽略；不改写历史链接、不覆盖用户已有材料。
