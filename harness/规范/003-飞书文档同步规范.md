# 飞书文档同步规范

## 授权与范围

JC 于 2026-09-05 明确要求将项目 docs 沉淀到飞书“健城”文件夹，以便随时和队友同步信息，并将约定写入 AGENTS.md。

- 目标父目录：AlxOrigin Team / [健城](https://my.feishu.cn/drive/folder/TuMLfPVhylk05pdAXzOcympwnWe)。其下使用 `Accord` 子目录，分类对应 `docs/`。
- 同步范围：`docs/**/*.md`，包括文档索引和同步台账；来源映射保存于 [飞书文档映射](../飞书文档映射.json)。
- 触发时点：Agent 新增或实质更新 docs 的同一任务，完成本地检查后、最终交付前同步；用户明确要求暂不发布的草稿除外。
- 持续授权限于这套项目文档、上述目录及必要子目录。不会自动发消息、改共享权限、转移所有权、发布到其他位置或创建后台任务。

## 结构与命名

```text
健城/Accord/
├── Accord-文档索引
├── 产品规划/
├── 竞品调研/
├── 技术架构/
└── 团队协作/
```

正文文档标题沿用本地文件名去掉 `.md`；同一主题不同类型仍复用编号。不用“最新”“最终版2”制造副本。更新已有文档必须优先使用映射中的 document_id，而不是每次新建。

## 同步步骤

1. 读取相关 `lark-drive` / `lark-doc` Skill 及对应命令参考；使用飞书 CLI 的 user 身份。检查本地差异和发布范围，凭据只供 CLI 使用。
2. 从映射取目标 ID；新文档先列目标文件夹，确认没有同名文档。映射缺失但同名对象存在时先读取核实，不直接覆盖或重复创建。
3. 更新前获取云端最新正文、revision 和评论，与上次验证的正文哈希比较。若队友修改，保留云端内容，做局部合并并将有效修改同步回本地；语义冲突无法判断时只向 JC 询问冲突项。
4. 发布稿保留全文事实、表格、来源和未验证限制；将相对文档链接替换为映射中的飞书链接。本地文件 / localhost 链接改成明确的本地路径或本机访问说明，不伪装成队友可点击的服务。正文标注本地来源路径和同步日期。
5. 本地原始缓存、密钥、真实会话、数据库、运行日志不上传。截图需逐张确认仅含任务相关测试数据，作为正文证据时单独上传；不能顺带上传整个截图目录。Mermaid 在飞书中若只呈现代码，明确标注，并保留可读的文字解释。
6. 首次创建后写入正文；后续按最新 block / section 精确更新，保留评论、图片、引用和队友补充。不要用整篇 overwrite 作为默认同步策略。删除本地文档不自动删除飞书文档，改为记录归档建议。
7. 每次写入后回读正文，检查标题、关键结论、表格、链接、末尾和降级警告；列目标文件夹验证归档位置。成功才记录本地 SHA-256、云端正文 SHA-256、revision_id、验证时间和 URL。
8. 更新文档索引与同步台账；最终回复给出飞书入口、同步数量及失败项。局部失败时继续无依赖的文档，不能把 CLI 的请求受理当作内容发布成功。

## 映射与冲突

`harness/飞书文档映射.json` 保存文档和文件夹 ID、可访问 URL、相对路径、源文件哈希、云端回读哈希、revision 和最后验证时间。这些资源 ID 不是访问凭据；不保存 access token、Cookie 或 API Key。

完整回读响应和发布中间稿放 `.local/feishu-publish/`，不提交。哈希用于识别变化，不代表授权判定；即使正文未变也要留意新增评论。不要为了自动同步清掉评论或重建文档。

## 本地与云端的关系

本地 docs 用 Git 记录工程事实，飞书副本便于队友阅读、评论和协作。队友有价值的修改应回收，不以“本地是源”为理由覆盖。默认在 Agent 任务交付时同步；自动文件监听、定时发布或完全自动双向合并须另行实现，当前并未启用。
